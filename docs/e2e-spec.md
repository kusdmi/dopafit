# Каталог браузерных проверок DopaFit

Это каталог проверок реализуемого набора, **не отчёт о выполненных тестах**:
статус прогона даёт CI и `make e2e-issues`, правила написания тестов —
[docs/TESTING.md](TESTING.md). Область работ: веб-приложение через настоящий
браузер, реальный API и две роли (клиент и тренер). Нативные сборки, тесты
только API и имитация интерфейса через MSW сюда не входят.

## 1. Цель и границы

Сделать воспроизводимый набор из **152 атомарных браузерных проверок**.
Проверять действия пользователя в UI и результат в UI после обновления,
повторного входа или в другом аккаунте. Сетевые ответы и данные API допустимы
как **дополнительное доказательство** сохранения, ошибок и контроля доступа;
они не заменяют действия через браузер. Набор должен ловить как функциональные
регрессии, так и уже найденные дефекты из `e2e/support/known-issues.ts`.

В наборе только то, что проверяется автоматически: ручных прогонов в проекте
нет, а неавтоматизуемый сценарий просто не входит в объём и не превращается в
чек-лист для человека. Прогон идёт против локального изолированного контура
(§2); развёрнутые стенды тестами не трогаются. Если ожидаемое поведение функции
требует продуктового решения, неизвестное правило сначала согласуется в
контракте/документации, а затем закрепляется точным оракулом; запись о
подтверждённом дефекте — в `e2e/support/known-issues.ts`.

**Источники истины:** [правила разработки](DEVELOPMENT.md),
[архитектура](architecture.md), [OpenAPI](../contracts/openapi.json),
[дизайн-система](design-system.md), [правила тестирования](TESTING.md)
и реальные маршруты `frontend/src/app/router.tsx`. Перед реализацией каждой
проверки сверять допустимые поля и статусы с актуальным контрактом; каталог не
фиксирует внутренние детали, которые могут измениться.

## 2. Требования к тестовому контуру

1. **Запуск:** Playwright в Docker через `make` (`make e2e-up`, `make e2e`,
   `make e2e-smoke`, `make e2e-pwa`); проектные `node`/`pnpm` на хосте не
   запускаются. Команды и отладка — [docs/TESTING.md](TESTING.md) §3 и §13.
2. **Контур:** собственная база `dopafit_e2e`, отдельные `backend-e2e` (:8100) и
   `frontend-e2e` (:5273), `VITE_API_MOCK=false`, снятые лимиты
   `DOPAFIT_CODE_SEND_*`, `DOPAFIT_ACCESS_TOKEN_TTL_MINUTES=1`. База
   пересоздаётся перед прогоном, поэтому начальное состояние известно.
   Платёжный провайдер на стенде только `mock` (`DOPAFIT_PAYMENT_PROVIDER`),
   реальных списаний не происходит — PAY-01…06 автоматизируются полностью.
   PWA и service worker проверяются только против прод-бандла
   (`make e2e-pwa`): в dev service worker выключен.
3. **Браузер:** Chromium как обязательная матрица. Desktop 1440×900 и mobile
   touch 390×844; критические формы дополнительно 320×700, крупный мобильный
   430×932. Два аккаунта — два независимых browser context; в тестах
   синхронизации — две вкладки одного контекста. Наличие `isMobile` и
   `hasTouch` в эмуляции обязательно фиксировать в отчёте.
4. **Данные:** прогон получает уникальный `runId`; все создаваемые
   имена/адреса помечены им. Код подтверждения в dev — `000000` (дефолт
   `DOPAFIT_DEV_VERIFICATION_CODE`); почтового канала нет — вне production код
   печатается в лог backend. У демо-аккаунтов сида способ входа —
   `login_method: "password"`, вход по коду для них невозможен: для
   OTP-сценариев регистрируется свежий аккаунт. Через UI делается то, что сам тест и
   проверяет, остальное готовят фикстуры `e2e/fixtures/` запросами —
   состав и правила в [docs/TESTING.md](TESTING.md) §4.
5. **Независимость:** тесты стартуют из известного состояния и не зависят от
   порядка соседних тестов. Восстанавливать разрешения, сеть, связь аккаунтов и
   настройки даже при падении. Несовместимые мутирующие сценарии изолировать по
   аккаунтам и запускать последовательно. Очистка только собственных данных
   `runId`; незавершённая очистка — отдельный сбой инфраструктуры.
6. **Оракул результата:** у каждого теста есть видимый итог, состояние после
   повторного открытия, при необходимости состояние второй роли, ожидаемый
   HTTP-статус и отсутствие лишних записей. Проверять точные значения,
   идентификаторы или число записей, а не только наличие текста «Успешно».
   Ошибки 4xx/5xx оценивать по конкретному сценарию; ожидаемый 422 не должен
   маскировать неожиданный 500. Не строить тесты на фиксированных UUID,
   произвольных `sleep` или строках CSS-классов.
7. **Надёжность:** ожидать наблюдаемого события (видимый UI, response,
   запись в истории, переход URL), задавать явные пределы времени. Повторять
   из-за сетевой задержки только безопасное чтение; мутации не повторять
   автоматически. В сценариях eventual consistency указывать предельное время
   и интервал опроса. Проверять `pageerror`, критические сообщения консоли,
   неожиданные неуспешные запросы и горизонтальное переполнение на mobile.
8. **Артефакты:** HTML/JSON-отчёт, trace и скриншот при ошибке, краткий
   сетевой журнал с методом, URL-шаблоном и статусом; без `Authorization`,
   паролей, одноразовых кодов, персональных данных, тел сообщений и фото.
   Исход каждой проверки — `passed`, `failed` либо известный дефект
   (`test.fail()` с ID из `e2e/support/known-issues.ts`). Журналы прогонов
   руками не ведутся: историю хранит CI, сводку дефектов — `make e2e-issues`.
9. **Селекторы:** только доступное имя, `data-testid` — последнее средство;
   правила целиком — [docs/TESTING.md](TESTING.md) §5.

## 3. Каталог тестов

Обозначения: **P0** — критический путь или безопасность; **P1** — основная
функция; **P2** — границы, устойчивость или представление. Каждый пункт — один
самостоятельный тест, кроме явно названного сквозного перехода между ролями.
Для всех тестов: проверять отсутствие неожиданной ошибки страницы и сохранять
доказательство при падении.

пакеты. Для заведомо текущих дефектов тест остаётся в наборе как ожидаемо
падающий **с явным ID дефекта** (`knownIssue`, `docs/TESTING.md` §9); не
скрывать его общим `skip` и не включать ожидаемое падение в зелёный релизный
сигнал.

## 5. Критерии приёмки реализации

- Каждый из 134 ID имеет файл/тест-кейс; нет «закрытых» сценариев без запуска
  соответствующих шагов.
- Каждый тест воспроизводится из чистого состояния и даёт один из трёх исходов:
  `passed`, `failed` либо известный дефект (`test.fail()` с ID из
  `e2e/support/known-issues.ts`).
- Для каждого P0 есть положительный и необходимый отрицательный оракул;
  в двухаккаунтных тестах сравниваются обе стороны, в тестах записи — данные
  после повторного открытия.
- Проверки UI и реального API идут в браузере; все тестовые секреты скрыты;
  артефакты не раскрывают чувствительные данные.
- Два подряд полных прогона на пересозданном контуре дают одинаковые результаты
  без flaky-падений. Подтверждённый дефект — запись в
  `e2e/support/known-issues.ts` плюс падающий тест; сводка — `make e2e-issues`.
  Журналы прогонов не ведутся: артефакты даёт Playwright.
- Для изменений продукта проходят обязательные `make`-проверки из
  `docs/DEVELOPMENT.md`, включая актуальный контракт.
