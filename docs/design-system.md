# Дизайн-система

Спецификация визуального слоя DopaFit: значения токенов, параметры компонентов и
правила переноса макетов в код.

**Источник правды по значениям** — переменные в макетах Figma:
`https://www.figma.com/design/DwU5LHwJXacc5uHhESArT1/v1`, канва «My tern (R) + DS»,
DS-фрейм — узел `661:1989`.
**Источник правды по реализации** — `frontend/src/app/styles/index.css`.

Этот документ фиксирует, что именно взято из макета, и отмечает места, где макет
неполон или противоречив, — чтобы решения не принимались заново на каждом экране.

⚠️ Кастомные классы компонентов (`.action-button*`, `.app-field*`, `.page*`,
`.bottom-nav*`, `.segment*`, `.dialog*`, `.toolbar*`, `.history-back`, `.avatar`
и т.п.) в `index.css` живут в `@layer components`. Это ниже `@layer utilities`
Tailwind в каскаде — благодаря этому Tailwind-утилита на том же элементе может
корректно перебить кастомный класс (например, `Button.tsx` переопределяет форму
`.action-button` обычными классами `rounded-[14px] px-5 …`, без `!important`).
При добавлении нового кастомного класса в `index.css` его тоже нужно класть
внутрь `@layer components` — иначе он снова начнёт молча выигрывать у утилит
независимо от специфичности. Исключение — `@theme`, `:root`, блоки тем
(`:root[data-theme=…]`, `@media (prefers-color-scheme)`) и `@font-face`: они
объявляют только custom properties/шрифты и слоёв не касаются.

## Как переносить экран из Figma

1. `get_design_context` на узел экрана — вернёт эталонный React+Tailwind и токены узла.
2. Реализовать через существующие примитивы (`shared/ui/primitives.tsx`,
   `shared/ui/Button.tsx`, `shared/ui/text-field/`) и семантические токены.
   Возвращённый код — **референс, не для вставки**: там абсолютное позиционирование
   и хардкод-хексы.
3. `get_screenshot` того же узла — сверить результат.

### Иконки

Интерфейсные иконки берутся из `lucide-react` через реэкспорт в
`frontend/src/shared/ui/icons.ts` — отдельных SVG-файлов проект не держит.

Порядок при переносе экрана:

1. Найти подходящую иконку в `lucide` и добавить реэкспорт в `icons.ts`.
   Совпадения по смыслу достаточно — попиксельное соответствие макету не требуется.
2. Только если в `lucide` нет ничего близкого (фирменный знак, иллюстрация) —
   скачать SVG из Figma и положить в `frontend/public/icons/`.

⚠️ Ссылки на ассеты из `get_design_context` живут ~7 дней: скачивать сразу,
ссылаться на URL Figma в коде нельзя.

## Цвет

Значения — из переменных Figma. В коде живут в `@theme` и блоках тем.

### Акцент («Основной цвет»), база — ступень 400

| Ступень | Hex | | Ступень | Hex |
|---|---|---|---|---|
| 50 | `#FFF0E6` | | 500 | `#D95C00` |
| 100 | `#FFD4AD` | | 600 | `#A84700` |
| 200 | `#FFB374` | | 700 | `#7A3300` |
| 300 | `#FF8C3A` | | 800 | `#4D2000` |
| **400** | **`#FF7003`** | | | |

В Figma ступень 400 помечена звёздочкой — это базовый акцент. Ступень 500 темнее и
акцентом **не является**; она используется как отдельный цвет серии графика
(`features/analytics/`), менять её на 400 нельзя — серии сольются.

В `@theme` заведены только ступени, у которых есть потребители: 50, 400, 500,
600. Остальные (100/200/300/700/800) — часть палитры Figma, но в коде их не
держим: Tailwind-токен без единого использования не генерирует ни одного класса
и живёт мёртвым объявлением. Понадобится ступень — добавить её в `@theme` из
таблицы выше.

### Нейтральная шкала — тёплая

| Ступень | Hex | | Ступень | Hex |
|---|---|---|---|---|
| 50 | `#FAFAF8` | | 500 | `#6E6A64` |
| 100 | `#F2F0EC` | | **600** | **`#46433E`** |
| 200 | `#D9D9D9` | | 700 | `#27251F` |
| 300 | `#C2BEB5` | | 900 | `#161412` |
| 400 | `#9A9690` | | | |

Вся шкала тёплая (R > B на каждой ступени) — в отличие от прежней холодной
серо-синей. Ступень 600 помечена в Figma звёздочкой как опорная.

**Ступени 800 в переменных Figma нет** (свотч на макете нарисован, но переменная к
нему не привязана). В коде она интерполирована между 700 и 900 и помечена
комментарием.

Шкала хранится как приватные переменные темы `--neutral-50`…`--neutral-900` (их
значения зависят от темы не напрямую — они статичны, а через них построены
тематические `--surface`/`--card`/`--line`/… алиасы). Дополнительно в `@theme`
заведены Tailwind-токены `--color-neutral-50`…`--color-neutral-900`, указывающие
на те же переменные — это даёт классы `border-neutral-500`, `bg-neutral-700` и
т.п. вместо `border-[var(--neutral-500)]`. Алиасы **намеренно перекрывают**
встроенную палитру `neutral` Tailwind (у неё несовместимые серо-синие hex) —
в проекте нет и не должно быть случаев использования стоковой Tailwind-палитры.

### Семантика

| Роль | 100 | 400 | 600 |
|---|---|---|---|
| Успех | `#D4F0D4` | `#2CA44E` | `#1A6B32` |
| Ошибка | `#FFE0E0` | `#E53535` | `#A82020` |
| Инфо | `#FFE5D0` | `#F5A623` | `#B57800` |

Ступень 400 — «заливочный» тон (белый текст на нём, кнопки/бейджи), а не цвет
текста на светлой подложке: контраст 400 на `card` в светлой теме — 2–4:1, ниже
WCAG AA. Поэтому текстовые алиасы **тематические**:

- `--color-success` / `--color-danger` / `--color-info` / `--color-brand-text`
  → тёмная тема: ступень 400 (как раньше); светлая тема: ступень 600
  (`brand-text` → `#A84700`).
- `--color-success-fill` / `--color-danger-fill` / `--color-info-fill` — НЕ
  тематические, всегда ступень 400. Используются, когда цвет — заливка кнопки/
  бейджа/сегмента чарта с белым/светлым текстом сверху (там контраст решает
  сочетание с белым, а не со `--card`).
- `--color-brand-400` (заливки, обводки) и `--color-brand` (легаси-алиас на 400)
  не меняются — заливки акцентных кнопок/чипов остаются на 400 в обеих темах.
- `--color-danger-on-card-light` и `--color-trainer-text` — тематические шаги
  для знака на `--card-light` (подложка на ступень светлее `--card`). Там
  обычные алиасы не дотягивают до 3:1 для нетекстовой графики: `--color-danger`
  в тёмной теме даёт 2.29:1, фиксированный `trainer-500` — 2.33:1 в тёмной и
  3.00:1 в светлой. `danger-on-card-light` → 100 в тёмной (7.97:1) и 600 в
  светлой (5.14:1); `trainer-text` → 400 в тёмной (3.62:1) и 600 в светлой
  (4.04:1). Для обводок и заливок остаются прямые ступени `trainer-400/500/600`.

Правило выбора: текст на `--card`/`--surface` → тематический алиас
(`text-success`, `text-danger`, `text-brand-text`); знак на `--card-light` →
`text-danger-on-card-light` / `bg-trainer-text`; заливка с контрастным текстом
сверху, или цвет линии в графике, который должен быть стабилен между темами →
`-fill`-вариант или прямая ступень (`-400`/`-500`/`-600`).

### Фон

```
основной (тёмная)   linear-gradient(to bottom, #1E1208, #161412 45%, #0E0B1A)
основной (светлая)  linear-gradient(to bottom, #FDF6EF, #FAFAF8 45%, #F4F2F8)
оверлей             linear-gradient(to bottom, #794299, rgba(0,0,0,0))
```

Тёмная тема — дефолт и источник истины, светлая выведена инверсией шкалы.

**Основной градиент — тематический.** Под ним лежит текст `--content`, поэтому
фиксированные тёмные хексы в светлой теме дают почти чёрное на почти чёрном
(контраст ~1.05:1). Реализован тем же приёмом, что `--brand-text`/`--success-text`:
приватная `--gradient-primary` переопределяется во **всех четырёх** блоках тем
(`@theme`-дефолт, `@media (prefers-color-scheme: light)`, `[data-theme='dark']`,
`[data-theme='light']`), а `@theme` держит только алиас `--gradient-bg-primary`.
Светлый вариант — зеркало тёмного по тёплой шкале: тёплый верх, `--neutral-50`
в середине, чуть холоднее к низу; `--content` на трёх стопах даёт 17.15 / 17.58 /
16.54:1. При правке градиента менять все четыре блока — иначе ломается та или
другая тема.

Оверлей-градиент (`--gradient-bg-accent`) тематическим делать не нужно: это
декоративная акцентная подложка без собственного текста. Сейчас в коде он не
используется ни на одном экране.

**`--gradient-bg-accent-solid`** — непрозрачный близнец оверлея для плашки, за
которой лежит контент, а не под которой. Нижний стоп оверлея — alpha 0, и баннер
активной тренировки (он `fixed` над таб-баром) просвечивал нижней половиной:
сквозь него читался контент страницы позади. Тот же фиолетовый и тот же верхний
стоп `#794299`, но низ — затемнённая ступень того же тона `#5C3275` вместо
прозрачности. Тоже не тематический: это акцентная плашка с собственным
фиксированным светлым текстом.

### Шапка на градиентных экранах

Экраны авторизации (welcome, вход, регистрация, восстановление пароля) идут на
основном градиенте (`<Page background="gradient">`), а шапка на них —
**прозрачная**: в макетах (392:2021 / 392:1972 / 392:2034) стрелка «назад» и
заголовок лежат прямо на градиенте, без плашки `--card` и без разделителя.

В коде это `<PageHeader transparent>` и аддитивный модификатор
`.page-header--transparent` (переопределяет `background` и `border-bottom` и
добавляет собственный верхний отступ, layout и safe-area остаются за
`.page-header`) — тот же приём, что `.page--gradient`. Дефолт у `PageHeader`
прежний, непрозрачный, так что остальные экраны не задеты.

Два уточнения, без которых «прозрачная шапка» ведёт себя по-разному на разных
экранах:

- **Отступ сверху — `env(safe-area-inset-top) + 10px`, а не только инсет.**
  У непрозрачной шапки воздух дают плашка `--card` и минимальная высота
  тулбара 44px; у прозрачной нет ни того, ни другого, а заголовки на этих
  экранах — H1 (22px, прежде Display 26px). Без фиксированного
  отступа зазор зависел от роли заголовка: 39px на «Замерах» против 60px на
  «Программах», причём на «Замерах» заголовок фактически лежал на верхней
  кромке. 20px давали уже слишком много воздуха — заметнее всего на экране
  тренировки, где под заголовком идёт вторая строка со временем.

  Отступ **симметричен**: одна переменная `--page-header-gap` раскладывается
  на обе стороны тулбара (снизу минус 1px на границу-разделитель), а
  `env(safe-area-inset-top)` прибавляется к верхней половине отдельно и в
  симметрию не входит. Величина сверена с макетом: в Figma тулбар — полоса
  44px (глиф стрелки 24px в тап-цели, y=81..105 → полоса y=71..115) на узлах
  `932:1941`, `1006:2005`, `1059:2001`, `1064:2035`, `1071:2094`, контент
  начинается на y=122, то есть под тулбаром макет оставляет 7px. Взято
  ближайшее значение сетки 5px — 10px. Итоговая высота шапки — 10 + 44 + 10 =
  **64px** (прежде 72px). Тулбар при этом не трогаем: его `min-height: 44px` —
  тап-цель кнопки «назад».
- **Прозрачная — значит по-настоящему прозрачная: ни скрима, ни блюра.**
  Прежде шапка несла скрим из `--surface` плюс `backdrop-filter: blur(8px)` —
  якобы чтобы проезжающий контент растворялся, а не обрезался. Но контент под
  шапку не заезжает вообще: `.page-header` — flex-сосед `main.page-content`, и
  скроллится именно `main`, начинающийся ПОД шапкой. Блюру нечего было
  размывать, а скрим просто закрашивал градиент непрозрачной полосой
  `--surface` — отсюда «шапка перекрывает градиент» и жёсткая кромка при
  прокрутке. Шапка лежит в общем потоке, фоновый градиент идёт под ней
  непрерывно.

  ⚠️ Если когда-нибудь понадобится, чтобы контент реально уезжал под шапку,
  одного скрима мало: нужен `position: sticky` + ненулевой `z-index` на
  `.page-header` и общий контейнер прокрутки. Полумера (скрим без
  позиционирования) — это то, что уже было и не работало.

Заголовок экрана живёт в шапке: `PageTitle` — это `<h1>` и **единственный**
`<h1>` на странице. Собственные заголовки шагов визарда и флоу внутри контента —
`<h2>`; дублировать текст заголовка шапки в контенте не нужно. Иерархию держат
тесты в `app/AuthFlows.test.tsx`.

Модалка — исключение: страница под ней не размонтируется, её `<h1>` остаётся в
документе, поэтому `Modal` передаёт `PageTitle level={2}`.

### Уровни заголовков экранов

Два уровня, больше не нужно:

| Уровень | Роль | Выключка | Где |
|---|---|---|---|
| 1 — корневой экран вкладки / раздела | H1 (22/700) | влево | Главная, Замеры, Тренировка (программы), Настройки (корень), Аналитика, Календарь, Клиенты, Уведомления, Все упражнения |
| 2 — вложенный экран (флоу, подстраница) | H2 (18/700) | по центру, под стрелкой «назад» | Подстраницы настроек и поддержка (через `PageShell` с `backHref`), авторизация, конструктор программы, тренировка, итоги, детали упражнения |

Уровень 2 — **дефолт** класса `.page-title`, поэтому вложенному экрану ничего
указывать не нужно: `<PageTitle>Заголовок</PageTitle>`.

Уровень 1 даёт общий компонент **`shared/ui/RootPageHeader`**: заголовок
`text-h1 text-left` плюс необязательная строка-пояснение ролью Body S
приглушённым цветом. Именно такую пару рисуют макеты корневых экранов —
«Frame 452» высотой 54px (заголовок 36px + Body S 18px): настройки
`1059:2004` / `1064:2038`, антропометрия `756:1979`, деактивация `1071:2097`.

Раньше этот блок жил по-разному на каждом экране: «Программы тренировок»
верстали его в шапке, «Данные антропометрии» и «Настройки» держали тот же по
смыслу текст ПЕРВОЙ СТРОКОЙ КОНТЕНТА (на настройках ещё и с компенсирующим
`-mt-2`), из-за чего шапки трёх корневых экранов не совпадали. Теперь все три
идут через `RootPageHeader`, и замер совпадает: высота шапки 85px, заголовок на
26px, подзаголовок на 54px, контент с 109px.

⚠️ `PageShell` выбирает уровень по наличию `backHref`: без него — корневой
экран и `RootPageHeader`, с ним — вложенный, тулбар с центрированным
заголовком. Подзаголовок имеет смысл только у корневого.

⚠️ Верхний отступ контента под шапкой задаёт только `.page-padding` (24px).
Своего `pt-*` у `PageShell` быть не должно: лишний `pt-6` опускал контент всех
одиннадцати экранов настроек и поддержки на 24px ниже, чем на экранах, которые
верстают `PageContent` напрямую (замерено: первый элемент на 120px против 96px
при прежней шапке). Шапка при этом выглядела одинаково, а отбивка под ней — нет.

**Уровень 1 — H1 (22/800→22/700), а не Display (26/800).** Продуктовое решение:
Display на корневых экранах занимал заметную долю первого экрана, а
единственный его потребитель — заголовок страницы. Разрыв с уровнем 2
(18px) остаётся читаемым: 22 против 18. Display как роль типографики
сохраняется (шаги регистрации, крупные значения в `Panel`, QR-код рефералки)
и из шкалы не убирается.

**Центровка уровня 2 — по экрану, а не по остатку строки.** `flex: 1` +
`text-align: center` центрируют заголовок внутри СВОБОДНОГО места: слева стоит
`HistoryBack` (min-width 44px), справа слота обычно нет, и визуальный центр
уезжал вправо примерно на 22px. Поэтому `.toolbar > .page-title:not(.text-left)`
позиционируется абсолютно с `left/right: 56px` (44px тап-цель стрелки + 12px
зазор с обеих сторон) — центр заголовка совпадает с центром экрана независимо от
того, есть ли справа действие. Длинный заголовок обрезается многоточием и не
доезжает ни до стрелки, ни до правого действия.

Два исключения, оба намеренные: `.text-left` (уровень 1 — заголовок владеет всей
шириной) и заголовок, вложенный НЕ прямым потомком `.toolbar` — на экране
тренировки `PageTitle` стоит в колонке вместе со строкой времени и должен
остаться в её потоке. Отсюда селектор через `>`.

⚠️ Название программы в шапке активной тренировки — **уровень 2 (H2)**, как и
у любого вложенного экрана: тренировку открывают из программы. Какое-то время
оно стояло на `text-h1` и после перевода корневых экранов на H1 22px сравнялось
с ними по размеру — переход «Программы» → «Тренировка» перестал читаться шагом
вниз по иерархии. Отдельной роли под него не заводим: два уровня закрывают
задачу, а разницу 22 → 18 поддерживает вторая строка со временем тренировки.

⚠️ Второе исключение выводит заголовок из-под правила, но **не отменяет самой
центровки по экрану** — её берёт на себя обёртка. На экране тренировки колонка
«название + таймер» позиционируется абсолютно теми же границами
`inset-x-[56px]`, что и одиночный заголовок, а `PageTitle` внутри получает
`max-w-full`, чтобы унаследованные `overflow: hidden` + `text-overflow: ellipsis`
обрезали длинное название вместо того, чтобы вылезать за колонку. Прежний
`flex-1` на обёртке центрировал её в остатке строки — то есть ровно та ошибка,
ради которой правило и вводилось: при 44px стрелке слева и пустом правом слоте
связка уезжала вправо примерно на 22px. Заголовок, вложенный в обёртку,
центровку по экрану не теряет — её просто нужно задать на самой обёртке.

Прежде `.page-title` задавал сырые `17px/600` — не роль дизайн-системы, из-за
чего экраны настроек и авторизации были мельче всех остальных, а всего размеров
заголовка на приложение набиралось четыре. Выключка тоже расходилась: список
программ шёл Display влево, а его же подстраница — H2 по центру, так что переход
родитель→ребёнок менял и размер, и выравнивание. Теперь смена уровня — это
осознанный шаг вниз по иерархии, а не разнобой.

⚠️ `PageTitle` остаётся единственным `<h1>` экрана; `Modal` передаёт
`level={2}`, и это про уровень ЗАГОЛОВКА В DOM, а не про визуальный уровень выше.

### Известные ограничения контраста

Следуют из значений макета, обходов не придумано:

| Пара | Контраст | Вывод |
|---|---|---|
| `muted` (400) на `card-light` (600) | 3.35:1 | `muted` только на `surface`/`card` |
| `danger` (400) на тёмной `card` (700) | 3.57:1 | ниже AA для обычного текста в тёмной теме; других ступеней danger в тёмной теме не заводили (базовая пара `danger` на `surface` — 4.28:1, приемлемо) |
| `info-text` (600) на светлой `card` | 3.26:1 | ниже AA для обычного текста (норма для крупного текста/UI, 3:1); `text-info` пока нигде не используется в коде |
| Текст `#FAFAF8` на заливке акцента | 2.65:1 | решение дизайнера; текст кнопки — 16px SemiBold |
| Точка личной тренировки (`brand-400`) на `card-light`, светлая тема | 1.97:1 | решение в пользу узнаваемости акцента, см. ниже |
| То же в недельной полосе на главной (`card-light/40`) | 2.37:1 | тот же случай, та же линия |

**Маркер личной тренировки — фиксированный `brand-400`, а не `brand-text`.**
Точка на календаре (`MonthGrid`), её образец в легенде (`CalendarStats`) и
точка в недельной полосе на главной (`WeekStrip`) красятся тем же оранжевым,
что и весь акцент приложения. Тематический алиас `brand-text` формально
держал порог (4.17:1 в светлой теме), но переворачивался вместе с темой на
ступень 600 — и точка переставала читаться акцентом, отличаясь по цвету от
всего вокруг. Это **нетекстовая графика** (порог 3:1), а не текст (4.5:1), и
здесь узнаваемость акцента важнее формального порога — та же логика, что у
светлого текста на акценте строкой выше.

⚠️ Сам токен `--brand-text` при этом не трогаем: он нужен и остаётся ТЕКСТОВЫМ
(ссылки, названия, чипы фильтра, реферальный код — около 28 мест), где порог
4.5:1 обязателен и чистый `brand-400` его не проходит ни в одной теме.

**На сегодняшней ячейке точка не перекрашивается, а получает обводку.** Узел
`392:5206`: заливка точки `#FF7003` (тот же `brand-400`, что и сама ячейка) плюс
обводка `#FFF0E6` (`brand-50`). Раньше обе точки на сегодняшнем дне уходили в
нейтральные (`neutral-50` / `neutral-900`) ради контраста — но тогда личная
тренировка переставала быть оранжевой ровно в той ячейке, куда смотрят чаще
всего, то есть теряла признак, по которому её узнают во все остальные дни.
Обводка решает ту же задачу читаемости (`brand` на `brand` — 1:1), не трогая
цвет-смысл; клиентская точка получает такую же обводку поверх своего
фиолетового. Правило действует и в `MonthGrid`, и в `WeekStrip`.

Клиентская точка остаётся на `trainer-text` (3.62:1 тёмная / 4.04:1 светлая):
её цвет под вопрос не ставился. По яркости пара «личная vs клиентская» близка
(1.02:1 тёмная, 2.05:1 светлая), различают их оттенок и позиция.

Исправлено (было в этом списке, стало тематическим — см. «Семантика» выше):
акцент/успех/ошибка на светлых `card`/`surface` теперь читаются через
`brand-text`/`success`/`danger` (ступень 600 в светлой теме, 5.2–7:1) — речь
про ТЕКСТ; про маркеры-точки см. исключение выше.

## Вложенность карточек

Обводка — структурный признак: она говорит «это отдельный объект». Когда
обведённый блок лежит внутри обведённого, признак теряет смысл: читатель видит
два объекта одного ранга там, где объект один.

**Правило.** У вложенного элемента — либо заливка без обводки, либо ничего.
Два уровня рамок на экране — потолок, три — дефект.

Что из этого следует на практике:

- Подложка под иконкой, медиа внутри карточки, тихая кнопка внутри
  обведённой карточки — **заливка** (`bg-card-light`, тонированная
  `color-mix` подложка), без `border`.
- Пустое состояние внутри карточки — просто подпись в той же области, без
  собственной рамки: отсутствие данных не объект. Пустое состояние **экрана**
  (никаких карточек вокруг) рамку иметь может — там она первый уровень.
- Подложка под иконкой держится по размеру глифа (круг ~38px), а не во всю
  ширину карточки: плашка во всю ширину сама читается карточкой независимо
  от того, есть у неё обводка или нет.
- Карточка с графиком внутри получает **уменьшенный боковой отступ**
  (`px-2` против `py-4`): боковые поля складываются из отступа страницы и
  отступа карточки, и каждый px съедает ширину области построения. Полный
  отступ держит заголовок карточки собственным `px`, а график забирает всю
  доступную ширину. Сам график рамки не имеет (`LineChart`).
- **Третий уровень может быть вообще без подложки.** Карточка параметра в
  «Антропометрии» (`ParameterCard`) лежит внутри обведённой `ChartCard` —
  обводка ей запрещена правилом выше, но и заливка `bg-card-light` оказалась
  плохим решением: сплошное серое пятно читалось тяжелее обведённой карточки
  вокруг него, а `muted` на `card-light` даёт 3.35:1 в тёмной теме — ниже
  порога 4.5:1 для текста (см. «Известные ограничения контраста»). Подложка
  снята совсем: подписи ложатся на фон страницы и дают 6.23–6.60:1 в тёмной
  теме и 8.86–9.42:1 в светлой. Группировку держат отступ и цветная точка
  серии. Разделители вместо заливки не подошли: `line` на `card` — 1.56:1 в
  тёмной и 1.63:1 в светлой, ниже порога 3:1 для нетекстовой графики.
- Сетка на две колонки включается, только когда элементов больше одного:
  жёсткий `grid-cols-2` с единственным элементом оставляет половину ширины
  пустой (карточка параметра в «Антропометрии»).

## Плотность и вертикальные отступы

Расстояние — такой же структурный признак, как обводка: оно говорит, насколько
элементы связаны. Одинаковый шаг между строками списка и между разделами
стирает разницу, а слишком крупный шаг внутри списка не даёт его сканировать.

| Что отделяем | Шаг |
|---|---|
| Однородные строки одного списка | **10px** |
| Заголовок раздела внутри списка, действие в конце списка | **12px** (свой `mt`) |
| Разные блоки экрана (список → отдельное действие, день → день) | **24px** |
| Крупные смысловые зоны (форма → история) | **25px** и выше |

Тап-цель строки списка — не ниже **44px**; строка с двумя строками текста при
`p-[10px]` выходит ~50px, чего достаточно.

Было: на списке программ шаг между карточками 25px, а до кнопки «Все
упражнения» — 50px; четыре программы занимали экран целиком, а промежуток
между соседними однородными строками читался как граница разделов. Внутри
программы упражнения дня шли с шагом 20px по той же причине.

## Модалки: попап или полноэкранный лист

Два варианта одного `Modal` (`shared/ui/Modal.tsx`, проп `variant`), геометрия —
в `overlays.css`.

**Попап** (`variant="popup"`, узлы `1119:2607`, `392:2618`, `392:2820`) —
карточка по центру: короткий список опций или форма в пару полей.

```
ширина    100% минус поля страницы (48px), но не шире 448px (max-w-md)
радиус    25px
padding   25px, gap 15px
шапка     заголовок H1 (22/700) слева + крестик 32px справа
max-height 70vh, содержимое скроллится внутри карточки
плашка опции: радиус 15px, padding 10px;
             выбранная — заливка chart-4 под chart-4-fg, остальные — card-light
```

Ширина тянется до краёв контентной колонки, а не фиксируется макетными 350px:
на узком телефоне попап должен идти по тем же краям, что и контент под ним, а
на планшете/в вебе — не растягиваться через весь экран.

**Полноэкранный лист** (по умолчанию) — визарды, длинные формы, всё, что
реально скроллится: `AddToProgramModal`, `CreateExerciseModal`,
`ExerciseModal` (в нём абсолютный дропдаун автокомплита, который обрежется в
карточке), `MeasurementDetailModal`, формы календаря.

Критерий — фактическое содержимое, а не тип окна: если контент укладывается в
карточку целиком, полноэкранный лист оставляет девять десятых экрана пустыми.

**Диалог подтверждения** (`ConfirmDialog`) — тот же попап, вопрос «да/нет» без
своей вёрстки: коробка, радиус и отступы общие (`--dialog-card-*` в
`overlays.css`), заголовок H1 слева, две кнопки во всю ширину карточки —
контурная «Отмена» и залитая с действием. Раньше у него была собственная
карточка 360px с радиусом 15px, и «Выйти из аккаунта?» рядом с обычным попапом
читался как окно из другого приложения. Крестика нет: у вопроса «да/нет»
закрытие — это «Отмена».

Подпись кнопки называет ДЕЙСТВИЕ («Завершить», «Удалить», «Отвязать»), а не
отвечает «Да»/«Нет»: заголовок тогда не приходится перечитывать, чтобы понять,
что произойдёт. Необратимое действие — `destructive`.

Все «да/нет» вопросы идут через `ConfirmDialog`. Собственного окна через
`useAlert` в экранах больше нет: там кнопки рисовались голым `action-button`
без вариантов, поэтому «Отмена» и «OK» выглядели одинаково.

## Тени

Тень кодирует **уровень над плоскостью экрана**, а не важность и не «кнопочность».

| Что | Тень |
|---|---|
| Элемент в потоке контента (кнопка внутри карточки, поле, чип, таб) | нет |
| Главное действие экрана, лежащее на фоне страницы | `--shadow-raised` |
| Оверлей над контентом (диалог, тост, всплывашка) | `--shadow-overlay` |

Токены в `index.css`:

```css
--shadow-raised:  0 6px 16px rgba(0, 0, 0, .18);
--shadow-overlay: 0 12px 32px rgba(0, 0, 0, .28);
```

Прежние значения из макета (`0 20px 25px` у основной кнопки и `0 20px 50px` у
вторичной) не сохранены намеренно. 20px вертикального смещения при 25px
размытия даёт оторванное от кнопки тёмное пятно ниже неё — на светлой теме это
хорошо видно («Добавить клиента»), а разное размытие у двух вариантов ОДНОЙ
кнопки кодирует разницу, которой нет: сплошная и контурная кнопки стоят на
одном уровне. Оба варианта берут `--shadow-raised`, и обе теряют тень, когда
лежат внутри карточки.

### Экран аналитики — два режима, без окна настроек

Аналитика (`pages/analytics/AnalyticsPage.tsx`) показывает ОДИН режим за раз —
«Тренировки» или «Антропометрия», — и все параметры выбираются прямо на
странице. Узлы: `768:1058`, `784:1093`, `786:1531`, `786:2076`, `790:2522`,
`790:3333`, `793:4331`, `852:1812`.

Окна «Настроить графики» больше нет. Оно и не было нарисовано: проверены все
перечисленные узлы плюс `852:1520` («графиков нет») — модалки настройки среди
них не существует, настройки лежат на самом экране строками «подпись Body S над
полем 52px». Вместе с окном ушли видимость, порядок и период каждой карточки —
их некуда было положить в макете.

Состояние экрана живёт в URL (`features/analytics/view/useAnalyticsView.ts`), а
не в `analytics_config`: экран переживает перезагрузку, им можно поделиться
ссылкой, и переключение вкладки не стоит запроса на сервер. Ключи `home_*` в
`analytics_config` при этом не тронуты — их читает Главная.

**Одна карточка на упражнение.** В режиме «По программе/дню» каждое упражнение
дня получает свою карточку с графиком и своими «Средний вес / Средний повт. /
Общее кол-во». Прежний эндпоинт `/analytics/workouts/series` так не умеет: он
усредняет все упражнения дня в одну точку, и день из жима 60кг и подтягиваний
10кг приезжал как 35кг — число, не описывающее ни одно из двух упражнений.
Поэтому добавлен `/analytics/workouts/series-by-exercise`, отдающий по серии на
упражнение (форма скопирована с `ParameterSeries` антропометрии). Старый
эндпоинт оставлен — его читает Главная.

**Отступления в контролах.** Два места, где макет нарисован иначе:

- «Дата» / «Период анализа» — в макете одно поле `00.00.2000 - 00.00.2000` с
  иконкой календаря, то есть кастомный range-picker. Вместо него два нативных
  `<input type="date">`, оформленных как одна строка: нативный пикер приносит
  системную доступность и локализацию на iOS и Android, а своя реализация
  повторяла бы это всё заново.
- «Выберите замеры» — в макете поле со списком `Вес, Талия, Грудь`, то есть
  мультиселект. Вместо него чипы: `<select multiple>` на телефоне почти
  неработоспособен, а чип несёт цвет своей серии — именно он связывает выбор
  здесь с линией на графике ниже.

Последний выбранный замер не снимается: пустой выбор дал бы пустой график без
объяснения, почему он пуст.

### Осознанные отступления от макета

Расхождения с Figma, оставленные намеренно. Каждое зафиксировано здесь, чтобы
его не «починили» обратно, приняв за недосмотр.

**Обводка выбранной темы — `border-success` вместо ступени 600.** На экране
`pages/settings/theme` выбранная карточка обводится классом `border-success`.
Это тематический алиас (ступень 400 в тёмной теме), а в макете обводка нарисована
ступенью 600 — разница в один шаг палитры.

Оставлено как есть. `success` — семантический токен, его используют и другие
экраны; подкрутить его ступень ради одного экрана нельзя, а заводить отдельный
алиас ради вкусовой разницы в один шаг — не оправдано. Отдельные алиасы в этой
системе появляются, когда без них не вытягивается контраст (`--brand-text`,
`--trainer-text`, `--danger-on-card-light` — см. «Семантика»); здесь контраст в
порядке и функционально всё работает, так что повода нет.

## Сервисные email-письма

Семь вариантов подтверждений используют общий шаблон в
`backend/src/platform/email/verification.ts`: регистрация, вход, восстановление
пароля, подтверждение и смена почты, смена способа входа, удаление аккаунта.
Тема и заголовок объясняют действие; прехедер дополняет их без раскрытия кода.

- Тёплая нейтральная палитра, фирменный `brand-400`, официальный логотип DopaFit
  из приложения: синий знак и оригинальное начертание. `frontend/public/logo.svg`
  растеризован в PNG 2×; цвета знака взяты из
  `--color-logo` / `--color-logo-fg`. Светлый и тёмный варианты используют цвет
  текста соответствующей темы. PNG встраиваются в SMTP-письмо через CID;
  внешних запросов для их загрузки нет. При блокировке изображений остаётся alt «DopaFit».
  Светлая тема: `surface` = neutral-100, `card` = neutral-50,
  `content` = neutral-900, `muted` = neutral-500. Тёмная: neutral-900,
  neutral-700, neutral-50, neutral-300 соответственно.
- Карточка до 560px, радиус 16px, отступы 40/36px на компьютере и 24/28px
  на телефоне. Заголовок 30/38px, на телефоне 26/34px; основной текст 16/26px.
- Код — непрерывный текст в моноширинном шрифте, 42px (36px на телефоне),
  на акцентной подложке с обводкой. Цифры не разбиваются на отдельные элементы:
  выделение и копирование сохраняют код целиком.
- Manrope используется при наличии на устройстве; далее системные шрифты.
  Внешние шрифты и изображения не загружаются. Основная информация — текст.
- Вёрстка таблицами с `role="presentation"`, базовые стили встроены в элементы.
  Для email семантические цвета разрешаются в конкретные значения при рендеринге:
  CSS-переменные приложения не требуются почтовому клиенту. Тёмная тема через
  `prefers-color-scheme`; если клиент её игнорирует, остаётся базовая светлая.
  Почтовые клиенты также могут самостоятельно преобразовывать цвета.
- Срок действия берётся из auth-конфига. После кода — инструкция вернуться
  в приложение и предупреждение о безопасности. Отдельных ссылок для входа,
  рекламных кнопок и информационного письма о входе по паролю нет.

PNG-логотипы хранятся в `backend/src/platform/email/assets` и копируются
в backend-сборку. При смене официального логотипа обновлять оба варианта:
тёмный текст для светлой темы и светлый для тёмной, геометрия исходного SVG сохраняется.
Узкая вёрстка сохраняется и при удалении почтовым клиентом блока `<style>`:
базовые inline-стили рассчитаны на телефон, медиазапрос расширяет их для компьютера.

Технические ограничения: [Gmail CSS](https://developers.google.com/workspace/gmail/design/css),
формат HTML + plain text: [Nodemailer](https://nodemailer.com/message).
Встраивание логотипа: [Nodemailer — embedded images](https://nodemailer.com/message/embedded-images).

### Реализация: `--text-*`, не `--font-*`

В Tailwind v4 неймспейс `--font-*` в `@theme` означает **font-family**, а не
«шрифтовую роль» — переменные вида `--font-h1-size`/`-weight`/`-line-height` не
попадают ни в один системный неймспейс и tree-shake'аются: не доезжают ни до
`:root`, ни до какого-либо класса.

Канонический способ задать размер+интерлиньяж+насыщенность одним токеном —
неймспейс `--text-*` с составными суффиксами `--line-height` и `--font-weight`:

```css
--text-h1: 22px;
--text-h1--line-height: 1;
--text-h1--font-weight: 700;
```

Каждая роль — одна переменная-размер плюс два суффикса, итого 3 объявления на
роль (33 всего на 11 ролей). Использование в компонентах — один класс на роль:
`text-display`, `text-h1`, `text-h2`, `text-h3`, `text-stat`, `text-stat-s`,
`text-body-m`, `text-body-s`, `text-label`, `text-caption`, `text-tag`. Каждый
класс задаёт `font-size` + `line-height` + `font-weight` одновременно — отдельно
задавать вес или интерлиньяж не нужно (и не надо, чтобы не разойтись с Figma).

Так как классы приезжают из `@theme` (слой `theme`/`utilities`), Tailwind
генерирует их только когда видит использование в контенте (JSX/TSX-файлах) —
проверка сборки должна использовать реальный компонент, а не только `grep` по
`@theme`.

### Поле ввода (`756:1986`, `757:1991`…)

```
фон       прозрачный (без заливки)
обводка   1px solid нейтральный 500
радиус    14px
высота    52px
padding   10px 22px
текст     Manrope SemiBold 16px
подпись   НАД рамкой (не внутри)
```

Геометрия живёт в одном месте — `shared/ui/field.ts` (`fieldGeometry` /
`fieldClass`) и `.app-field` в `index.css`; менять её надо в обоих.

DS-узел поля (`392:5036`/`392:5047`) рисует 58px и обводку 2px, но экраны с
формами (антропометрия `756:1712`) задают поле компактнее — 52px и волосяную
обводку. Взят вариант экранов: двойная толщина и была источником «жирности»,
при десятке полей подряд рамка начинала читаться раньше значения. От толщины
контраст не зависит: `--neutral-500` (#6E6A64) против фона — 3.61:1 в тёмной
теме и 4.91:1 в светлой, обе выше порога 3:1 для нетекстовой графики. 52px
выше порога тап-цели 44px.

**Подпись — снаружи рамки.** Подпись внутри рамки (прежний `stacked-label`
фасада `Input`) складывает высоту подписи с высотой строки ввода: поле с одной
строкой значения выходило ~86px. Единица измерения («см», «кг») стоит
**вплотную к значению**, а не у правого края, иначе читается отдельным
элементом, а не единицей при числе.

С иконкой: `flex justify-between`, иконка 20×13.5px справа.

В макете поля показаны только пустыми — цвет введённого текста не задан.
Решение реализации: введённый текст — нейтральный 50, плейсхолдер — 500.

**Единица пользовательского поля — выбор из списка, не свободный ввод.**
Поле заводит сам пользователь, и текстовый ввод давал разнобой написаний
(«см» / «См» / «cm»), из-за чего значения разных записей переставали читаться
как один ряд. Список (`entities/measurement/model/units.ts`) закрывает то, что
реально меряют в антропометрии: `см`, `мм`, `кг`, `г`, `%`, `°`; по умолчанию —
`см`, самая частая единица обхватов. Контракт (`CustomFieldUpdateRequest`)
по-прежнему принимает любую строку 1..10 — ограничение только в интерфейсе,
поэтому единица, сохранённая раньше свободным вводом, подмешивается к списку
и не затирается при открытии поля.

**Смена даты перепривязывает всю форму.** Дата выбирает запись за этот день:
поля, которых в ней нет, очищаются, а не доносят значения предыдущей даты — это
касается и снимков. В коде пустые значения перечисляются поимённо
(`emptyValues`), потому что `reset()` пропускает ключи со значением `undefined`
и такие поля остались бы с прежним числом.

### Тумблер настроек (`.toggle`)

Нативный `<input type="checkbox">` без стилей браузер рисует системным
квадратным чекбоксом с тёмной галочкой — на экране уведомлений он читался
чужеродно, а в выключенном состоянии выглядел «белым квадратом в серой рамке».
`.toggle` переопределяет отрисовку: дорожка 44×26 с радиусом 13px и бегунок
18px, состояние кодируется **заливкой и положением бегунка**, а не одним цветом.

```
ВЫКЛ  дорожка --card-light, обводка 1px нейтральный 500, бегунок слева
ВКЛ   дорожка акцент 400,   обводка акцентом,            бегунок справа
```

Контраст (порог 3:1 для нетекстовой графики): обводка выключенной дорожки на
`--card` — 3.03:1 в тёмной теме и 4.60:1 в светлой; включённая дорожка — 5.52:1
и 3.25:1.

**Границу бегунка держит тень, а не обводка.** Бегунок `--neutral-50` на акценте
даёт 2.67:1 — ниже порога, поэтому раньше он нёс собственную обводку нейтралью
500. Обводка читалась лишней рамкой вокруг круга. Вместо неё — тень
`0 1px 2px rgba(0,0,0,.55)` плюс `0 0 1px rgba(0,0,0,.45)`: как линия не видна,
но именно по ней теперь считается контраст. Самая тёмная точка ореола поверх
акцента `#FF7003` — это `#FF7003 × 0.45 = #723201`, и `--neutral-50` (`#FAFAF8`)
против неё даёт **8.14:1**. На выключенной дорожке (`--card-light`) тот же ореол
держит бегунок на 7.4:1 в тёмной теме и 9.6:1 в светлой. Все выше порога 3:1.

На экране уведомлений это **тумблеры, а не чекбоксы**: настройки применяются
сразу, без отправки формы. Отдельного макета этого экрана в Figma нет (узел
`392:2836` — лента уведомлений, не их настройки), так что решение принято по
семантике.

Карточка рекорда и график силового прогресса — **два независимых выбора**, в

начала (`record_exercise_id` / `strength_exercise_id`) — на клиенте просто не
передавался первый. Не сливать их обратно.

устроен фолбэк на бэкенде) — это ожидаемо и ломать не нужно.

Карточка с выбором («Личный рекорд») нажимается ЦЕЛИКОМ, а не только строкой с
плашкой и чевроном: кнопка растягивает `after` на весь родитель (`relative` на
карточке). Обёртывать всю карточку в `<button>` нельзя — внутри крупное
значение, которое пользователь может выделять, а вложенных интерактивных
элементов кнопка не допускает.

### Подпись изменения у графиков (`392:2101`, `392:2170`)

Две строки, обе выровнены вправо:

```
изменение в единицах   20px/700   «-2.5 кг» · «+10 кг»   ← знак ВСЕГДА, и «+» тоже
процент со стрелкой    12px/600   «↓ 3%» · «↑ 16.7%»
```

Проценты без единиц измерения показывать нельзя: по одному «3%» не понять, о
каких величинах речь. Абсолютное изменение считается на клиенте из тех же
точек, по которым backend вернул `change_percent` (последняя минус первая —
`domain/rules.ts`), поэтому знаки у двух строк всегда совпадают; отдельного
поля в контракте нет и не нужно.

Стрелка дублирует знак, чтобы направление не держалось на одном цвете, а
процент берётся по модулю — «↓ -3%» читалось бы как двойное отрицание.

**Цвет линии графика равен цвету подписи** и задаётся НАПРАВЛЕНИЕМ, а не
карточкой: падение — зелёный `--color-chart-3` (#2CD08A), рост — акцент
`--color-brand-400` (#FF7003), нет данных — `--color-muted`. Раньше у графиков
была своя фиксированная палитра (замеры оранжевые, сила фиолетовая), и зелёная
подпись висела над оранжевой линией. Таблица тонов одна на обе формы:
`TONE_COLOR` в `chart-card/delta.ts` (значение для SVG) и `TONE_CLASS` в
`ChartCard.tsx` (класс для текста) — расходиться они не должны.

### Безопасные зоны на iOS

Предложение обновить веб-приложение/PWA — постоянная немодальная карточка
`app-update-notice` над нижним стеком: поля 16px, padding 16px, gap 12px,
радиус 16px, тематические `card/content/muted/line` и `shadow-overlay`.
Карточка не исчезает по таймеру. Кнопка «Обновить» открывает стандартный
`ConfirmDialog`: «Обновить приложение?», действия «Позже»/«Обновить» и
предупреждение о сохранении открытых форм. Во время применения кнопки и закрытие
диалога заблокированы. Ошибка или причина отложенного обновления остаётся в
карточке; активная тренировка и несинхронизированные данные не прерываются.

**Единый фон документа и страницы.** `html` и `body` рисуют тот же
`--gradient-bg-primary`, что и `.page--gradient`; резервный сплошной цвет
`--chrome-bg` совпадает с верхним стопом градиента и подсказкой `theme-color`.
Цвет меняется вместе с темой, включая системную. До загрузки CSS в `index.html`
есть светлый/тёмный фон по предпочтению ОС. Без этого Safari может продолжить
плоский фон документа вокруг градиента и показать отдельные полосы.
Safe area добавляется к отступам элементов управления, а фон занимает весь каркас.
Нельзя маскировать полосы отрицательными отступами или высотой `screen.height`:
это уводит кнопки под системные панели и ломает клавиатуру.

Safari сам управляет адресной панелью и её материалом. `theme-color` — подсказка,
а не гарантия цвета во всех версиях Safari. Для запуска без адресной панели
предусмотрена установка PWA через «Настройки → Установить DopaFit».
Особенности заполнения зон описаны в [руководстве WebKit](https://webkit.org/blog/7929/designing-websites-for-iphone-x/),
продолжение фона возле фиксированных элементов — в [пояснении WebKit](https://bugs.webkit.org/show_bug.cgi?id=301756#c2).
UI-12 проверяет CSS-фон и отклик вкладок; браузерный тест не эмулирует системные панели iOS.

Две отдельные проблемы, обе видны только на устройстве — ни Chrome, ни
симулятор их не показывают, потому что `env()` там ведёт себя иначе.

**Сверху: воздух под вырезом ≠ макетный отступ.** `env(safe-area-inset-top)`
кончается по РАМКЕ выреза, поэтому макетные 10px (`--page-header-gap`) — это и
есть всё расстояние от часов до заголовка. На iPhone 14 Pro и новее логотип
зрительно липнет к Dynamic Island (у него ещё и скруглённые углы снизу).
Поэтому у прозрачной шапки есть второй токен `--page-header-air: 20px`, и
отступ считается как `inset + max(gap, air)`: на экране без выреза ничего не
меняется, под вырезом воздух становится 20px — сопоставимо с системными
экранами iOS. Тулбар и его тап-цель 44px не трогаются.

⚠️ `max()`, а не медиа-запрос: сравнить `env()` в `@media` нельзя.

**Снизу: единая высота каркаса и плавающих элементов.** Вкладка использует
`--app-height: 100dvh`; установленное PWA в WebKit — `100lvh`: динамические
единицы в standalone могут вычитать статус-бар даже при `viewport-fit=cover`.
`html` и `body` получают эту высоту, а `#root`, `.app-frame`,
`.protected-shell` и `.page` наследуют её через `height: 100%`.

`body` позиционируется абсолютно и имеет `contain: layout`: фиксированные
элементы, включая портальные диалоги, привязаны к тому же каркасу. Фиксировать
сам `body` нельзя — WebKit может обрезать его по уменьшенному viewport.
Документ закрыт `overflow: hidden` и `overscroll-behavior: none`; прокрутка
контента остаётся в `.page-content`, плавающая навигация сохраняет safe area.

Личные замеры обеих ролей занимают один `.page` без блоков перед ним:
внешний переключатель прибавляет высоту к странице и уводит её низ под
навигацию. Выбор клиента находится в аналитике. UI-10 проверяет доступность
конца контента основных вкладок, в том числе с активной тренировкой.

При фокусе в поле и существенном уменьшении `visualViewport` высота каркаса
сохраняется. Перекрытие клавиатурой задаёт дополнительное место и отступ прокрутки
в `.page-content`; активное поле поднимается над клавиатурой внутренним скроллом.
Нижняя навигация и плашка тренировки скрываются, диалоги используют видимую высоту.
После закрытия клавиатуры возвращается CSS-высота. Аппаратная клавиатура, масштаб
и поворот окна не должны давать ложный признак клавиатуры. Capacitor сохраняет
`KeyboardResize.Native`; глобальных перехватов `touchmove` нет. UI-08/UI-10/UI-11
проверяют геометрию в Chromium и desktop WebKit; системный UI iPhone не эмулируется.

**Значение инсета: следуем за актуальным, ноль игнорируем.** Нижний инсет
берётся из `--safe-area-bottom` (держит `shared/lib/platform/safe-area`,
подключён в App.tsx); `env()` остаётся фолбэком для веба. WKWebView на первых
кадрах отдаёт ЗАВЫШЕННЫЙ инсет (наблюдалось ~46px против настоящих 34px) и
уточняет его позже, поэтому переменная следует за текущим значением.

⚠️ Держать МАКСИМУМ нельзя — так завышенный стартовый инсет замораживается
навсегда (ровно эта ошибка и была допущена в первой версии фикса). Но и ноль
принимать нельзя: при показе клавиатуры (`resize: native`) WebView укорачивается
и инсет честно становится нулевым, отчего резерв схлопнулся бы на каждый фокус
в поле.

⚠️ Новые места, резервирующие низ, обязаны брать `var(--safe-area-bottom)`.
Прямой `env(safe-area-inset-bottom)` остался только там, где он безвреден
(оверлеи и модалки центрируются, а не резервируют полосу).

### Онбординг первого запуска (`392:1951`)

Экран открывается один раз — до приветствия, входа и регистрации, — и дальше
его закрывает флаг `useOnboardingStore` (`dopafit.onboarding` в `kvPrefs`).

**Сразу слайдер, хотя слайд один.** Всё содержимое — цитата, подпись, картинка
— лежит в `ONBOARDING_SLIDES` (`entities/onboarding/model/slides.ts`), а не в
разметке. Второй слайд добавляется элементом массива: «Далее» листает и
закрывает онбординг только на последнем, точки-индикаторы появляются сами,
когда слайдов становится больше одного (на единственном они были бы
управлением, которому нечего переключать).

**Флаг живёт в `kvPrefs`, а не в localStorage.** На native это Capacitor
Preferences, которые ОС не вычищает под нехваткой места, — иначе экран первого
запуска возвращался бы сам по себе. Флаг НЕ привязан к аккаунту и не сбрасывается
при выходе: онбординг смотрят до регистрации, и повторять его вышедшему из
аккаунта незачем.

⚠️ Стор обязан входить в `useStoresHydrated`. Сторадж асинхронный, и без
ожидания гидрации первый кадр приходит с `seen: false` — то есть онбординг
моргает на КАЖДОМ старте. Проверено обсервером до первой отрисовки: с гейтом
вспышки нет.

**Цвета — токены, а не фикс из макета.** В макете подпись `#D9D9D9`
(нейтральный 200) на тёмном градиенте, но взяты `text-content`/`text-muted` и
`Page background="gradient"`: сам градиент уже темизирован и в тёмной теме
совпадает с макетом точка-в-точку (`#1e1208 → #161412 45% → #0e0b1a`). Цена —
подпись в тёмной теме чуть глуше макета (`#9a9690`, контраст 6.25:1 против
13.02:1 у `#D9D9D9`), зато экран не ломается в светлой теме и не заводит
второй набор правил для одного экрана.

**Картинка — квадратный WebP 1000×1000 (~97 КБ) в `public/onboarding/`.** Спортсменка
с гантелью и оранжевой футболкой снята с запасом фона сверху и по бокам:
голова, локти и гантель остаются в центральной безопасной области кадра.
Ширина фотографии — до 350px. При высоте окна от 800px рамка имеет пропорцию
350:517, от 641 до 799px — квадрат, до 640px — 4:3. `object-cover` обрезает
фон в пределах этих пропорций; высота рамки не сжимается произвольно.
На очень низких экранах контент прокручивается внутри страницы, кнопка доступна.
В precache-манифест она намеренно не входит — экран показывается один раз, и платить за него
установкой у всех пользователей не за что.

### Модалка записи на тренировку (`392:4474`)

плашка поля   --card-light · радиус 15px · padding 10px

у него нет). Кнопка подтверждения у тренера фиолетовая (серия 4) — в системе
это цвет всего, что про клиентов.

**При создании дата — статичный текст, а не `readOnly`-инпут.** Её задаёт
выбранный день календаря, а `readOnly`-инпут скринридер объявил бы полем,
в которое нельзя писать. При редактировании существующей записи дата —
доступное поле, чтобы тренировку можно было перенести на другой день.
Время редактируется в обеих формах.

⚠️ Поле времени набрано `text-h3` (16px), а не `text-body-m` (14px) из макета:

При создании плашка «Дата» — не поле ввода, её 14px по макету оставлены.

что и поле времени.

### Нижняя навигация (`392:2229`)

Макет таб-бара **есть** — узел `392:2229` на главном экране. Прежняя редакция
этого раздела утверждала обратное и называла узел «виджетом активной
тренировки»: это была ошибка обхода. В узле лежат ДВА элемента — плашка
активной тренировки (`392:5261`) и под ней сам таб-бар (`392:5264`).

```
бар         высота 72 · боковые поля 16 · снизу max(8, safe area)
            тематический фон · радиус 20 · padding 14/12
плитка      44×44 · радиус 15 · активная — акцент 400, неактивная — тематическая
глиф        нейтральный 50 · 5 вкладок, подписей НЕТ
```

Бар плавает над контентом. Актуальная геометрия уточнена для iOS: высота 72px,
боковые поля 16px, нижний отступ `max(8px, safe area)` без дополнительного сложения.
Каждая ссылка имеет высоту и минимальную ширину 44px. Параметры задаются общими
`--bottom-nav-height`, `--bottom-nav-gutter`, `--bottom-nav-inset`; плашка активной
тренировки использует те же токены.

`--tab-bar-space` равен высоте панели плюс её нижний отступ, поэтому
`.bottom-nav` разделён на два элемента: внешний прозрачный слой держит поля,
видимая плашка — вложенный `.bottom-nav__bar`.

Нажатие вкладки меняет только её скруглённую плитку: масштаб 0.96 и прозрачность
0.8, переход 80ms. На широкой области ссылки нет ни фоновой вуали, ни системной
подсветки WebKit. `focus-visible` обводит плитку акцентом 2px с отступом 3px;
при reduced motion масштаб и переход отключаются, отклик прозрачностью остаётся.

**Подписей у вкладок нет** — их нет в макете. Правило «активность не только
цветом» от этого не нарушено: активная плитка отличается и заливкой, и
светлотой (в grayscale видно в обеих темах), имя вкладки ушло в `aria-label`
ссылки, а активная помечена `aria-current="page"`. Прежний механизм (жирная
подпись + обводка-пилюля) снят вместе с подписями — не возвращать его по старой
редакции этого раздела.

Цвета бара тематические — `--tab-bar-bg` / `--tab-bar-tile` /
`--tab-bar-tile-fg`, а не `--card`/`--card-light`: бар лежит ПОВЕРХ контента, и
ему нужен собственный тон плюс `--shadow-overlay`, иначе в светлой теме он
сливается с поверхностью. Активная плитка (акцент 400) и её светлый глиф
фиксированы в обеих темах.

Глифы вкладок лежат в `app/bottom-nav/glyphs.tsx` — они сняты с макета
(`235:481`…`235:485`), а не взяты из `lucide-react`: «Замеры» в макете планшет с
галочкой, «Тренировка» — диагональная штанга, и обе заметно расходятся с
ближайшими аналогами библиотеки. Подложка-`rect` из исходных SVG снята, её
рисует CSS; цвет глифа — `currentColor`. За пределами таб-бара иконочная
система прежняя — `shared/ui/icons.ts`.

Пятая вкладка нарисована гамбургером, но ведёт по-прежнему на «Настройки»:
отдельного экрана-меню нет, а настройки и так собирают «всё остальное».

### Плашка активной тренировки (`392:5261`)

Плашка **подтыкается ПОД бар**, а не стоит на нём: в макете у неё
`mb-[-45px]` при `pb-[53px]`, то есть 45px нижнего поля перекрыты баром и
видимыми остаются те же ~8px воздуха, что и сверху. Отсюда три следствия в
коде: скруглены все четыре угла (нижние просто не видны), плашка лежит ниже
бара по слою (`z-40` против `z-41`), а в `--active-plate-space` публикуется
только видимая над баром часть — иначе нахлёст резервировался бы дважды.

```
заливка   --gradient-bg-accent-solid (#794299 → #5C3275)
обводка   --accent-plate-line (#794299, тот же, что верхний стоп заливки)
текст     --color-brand-50 (#FFF0E6)
```

Вариант у плашки **один — фиолетовый**, независимо от роли. Раньше своя
тренировка рисовалась нейтральной карточкой, а фиолетовая доставалась только
тренеру; в макете такого деления нет — это «идёт тренировка», а не «идёт
тренировка клиента». Не возвращать нейтральный вариант.

Обводка — `--accent-plate-line`, а НЕ серия 4 (`#C96EFF`): в макете рамка
совпадает с верхним стопом заливки и лишь очерчивает низ, уходящий в тёмный.

Подпись участника выводится только для ЧУЖОЙ тренировки. На своей она была бы
«Я» — в собственном приложении это шум, и в макете её нет. Для скринридера имя
не потеряно: оно осталось в `aria-label` («Тренировка идёт: Я»).

Иконка вкладки «Замеры» больше не берётся из `icons.ts` — см. `glyphs.tsx`
выше. (Исторически там был `Ruler`, до него ошибочный `Accessibility` со знаком
доступности; к текущему бару это не относится.)

Названия вкладок — Главная · Замеры · **Тренировка** · Аналитика · Настройки.

Продуктовое решение по TC-037 принято: вкладка «Программы» переименована в
«Тренировка». Переименована **только вкладка** — заголовок страницы «Программы
тренировок» и секция «Программы клиентов» остаются прежними, сущность `program`
в API не меняется. Прежний запрет («менять нельзя до решения по TC-037») снят —
не откатывать переименование по старой редакции этого раздела.

## Отображение дат и периода бесплатной аналитики

### Каталог с подгрузкой

Каталог показывает единый список в серверном порядке, категорию — подписью строки;
верхние фильтры категории, поиска и избранного сохранены. Общий счётчик использует
`total` сервера. Отдельная строка занимает 100 px, название ограничено двумя строками
с полным доступным именем ссылки. Это позволяет сохранять положение при подгрузке
и возврате из карточки. Вместе с позицией возвращаются фильтры текущей записи истории
(до 20 записей). В DOM остаются видимые строки и небольшой запас для прокрутки.

В конструкторе результаты поиска и в аналитике список выбора используют строки
64 px в ограниченной области прокрутки. Аналитика открывает модальный поиск вместо
нативного select со всем каталогом. Состояния загрузки, ошибки с повтором и
незагруженной офлайн-страницы показываются рядом со списком. Цвета — семантические
токены в обеих темах; отметки избранного и их офлайн-очередь сохранены.


## Активная тренировка и ограничения Premium

Навигация «Предыдущее / Следующее» со счётчиком располагается отдельной строкой над
карточкой упражнения. В карточке у названия — нативный квадратный чекбокс с подписью
«Выполнено», кликабельной меткой и областью нажатия не меньше 44×44 px. Дублирующей
кнопки завершения нет. Поля «КГ» и «Повторы» имеют собственные рамки. Подсказка
таймера — popup с кнопкой «Понятно», без автоматического закрытия; таймер запускается
заново после записи нового подхода.

Ограничения Premium обозначаются общим `PremiumNotice`: текстовая метка Premium,
замок, пояснение и ссылка «Подробнее о Premium» в настройки подписки. Компактный
вариант открывает popup; численные лимиты указываются по серверным entitlements.
Бесплатный выбор ресурсов остаётся доступным на экране подписки. Загрузка и ошибка
проверки прав не отображаются как отсутствие Premium; офлайн используются сохранённые
права. Средний отдых, таймер и отправка результатов проверяют свои отдельные права.

На всех формах нового пароля видны одинаковые требования: 8–32 символов, заглавная
и строчная латинские буквы и цифра; дополнительные символы допустимы. На экранах
запроса и ввода кода входа показано общее пояснение о способе «пароль» и доступен
переход к паролю с сохранением email, без раскрытия существования аккаунта.

Категории упражнений: рамка чипа 1px, ряд не сжимается по вертикали и имеет
вертикальные отступы внутри горизонтального скролла. Состояние выбора доступно
через `aria-pressed`. Верхняя плашка аккаунта в настройках целиком открывает
«Личные данные» и содержит стрелку перехода.

### Установка приложения из браузера

В настройках выделена ссылка «Установить DopaFit»: брендовая обводка, значок
телефона, пояснение про экран «Домой». Она ведёт на отдельную страницу с выбором
устройства iOS/Android, четырьмя доступными шагами и кнопками перехода. На Android
при наличии `beforeinstallprompt` доступна системная установка по нажатию.
В установленном приложении карточка в настройках скрыта; прямой URL показывает
подтверждение установленного режима.

На главной мобильного браузера после 20 секунд появляется компактное предложение
над нижним меню. Оно не модальное, закрывается кнопкой с тап-целью 44px и ведёт на
ту же инструкцию. Период — не чаще раза в 7 дней, отметка хранится на устройстве и
переживает reload/смену аккаунта. В native, standalone, без сети, при активной
тренировке, вводе с клавиатуры или открытом диалоге автоматического предложения нет.
Подтверждённое `appinstalled` отключает дальнейшие напоминания в этом браузере.

Инструкции сверены с [Apple](https://support.apple.com/ru-ru/guide/iphone/iphea86e5236/ios)
и [Chrome](https://support.google.com/chrome/answer/9658361?hl=ru&co=GENIE.Platform%3DAndroid).
Отсутствие системного API установки не блокирует ручную инструкцию.
