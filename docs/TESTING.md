# DopaFit — тестирование

Единый источник правды о том, как проверять DopaFit. Документ адресован и людям, и AI-агентам:
правила здесь жёсткие, потому что проверки выполняются без участия человека.

**Ручных прогонов в проекте нет.** Всё, что проверяется, проверяется автоматически. Сценарий,
который нельзя автоматизировать, не входит в объём — он не помечается `blocked` и не превращается
в чек-лист для человека.

Каталог браузерных проверок — [docs/e2e-spec.md](e2e-spec.md). Общие правила разработки, DoD и
команды — [docs/DEVELOPMENT.md](DEVELOPMENT.md).

В CI тестовые прогоны запускаются по запросу через **Actions → Run workflow**:
`Tests and builds (manual)` — тесты и сборки backend/frontend, опционально Docker;
`E2E (manual)` — выбор `smoke`, `full`, `pwa` или `all` (full + PWA).
Выбор набора: `smoke` — критические сценарии для быстрой проверки перед слиянием;
`full` — все основные сценарии в dev-контуре; `pwa` — production-сборка,
service worker, офлайн-перезапуск, установка и push; `all` запускает `full` и `pwa`
отдельными CI jobs. Перед релизом и при изменении общего каркаса, роутинга или
PWA выбирайте `all`. `full` не включает проверки с тегом `@pwa`.
Автоматического e2e на PR и ночного расписания нет. Ручной запуск workflow запускает
автоматизированные тесты; проходить сценарии руками по-прежнему не требуется.

## 1. Три уровня и когда какой писать

| Уровень | Инструмент | Что проверяет | Где лежит |
|---|---|---|---|
| Backend | vitest, `app.request()` (Hono, без сети) | домен, HTTP-слой, права доступа, идемпотентность | `backend/tests-ts/*.test.ts` |
| Frontend | vitest + RTL + MSW | компонент, форма, хук, состояние стора | рядом с кодом, `*.test.tsx` |
| E2E | Playwright в Chromium | сквозной путь пользователя в реальном браузере против реального API | `e2e/specs/*.spec.ts` |

Правило выбора: **логика или слой → unit; экран против моков → frontend-тест; путь пользователя
через несколько экранов, две роли, офлайн, service worker или контроль доступа → e2e.**

Антипаттерн: дублировать в e2e то, что закрывает frontend-тест с MSW. Валидация полей, тексты
ошибок и состояния кнопки проверяются дешёвым тестом; e2e на это тратить нельзя — он на два
порядка дороже и идёт последовательно.

Обратный антипаттерн тоже реален: контроль доступа нельзя проверить моками. Если тренер не должен
видеть данные клиента — это e2e плюс backend-тест на запрет, а не тест компонента.

## 2. Два контура

`make up` — контур разработки: postgres, minio, backend `:8000`, frontend `:5173`, база `dopafit`.
Его состояние принадлежит разработчику, тесты его не трогают.

`make e2e-up` — контур e2e: собственная база `dopafit_e2e`, `backend-e2e` на `:8100`,
`frontend-e2e` на `:5273`. Отличия от dev заданы окружением:

- `VITE_API_MOCK=false` — MSW выключен, фронт ходит в реальный backend;
- межзапросный интервал и общие IP/суточные лимиты сняты (`DOPAFIT_CODE_SEND_*`), чтобы
  независимые регистрации не мешали друг другу; почасовой лимит для одного адреса равен трём,
  чтобы AUTH-05 проверял ответ 429 и понятный таймер повтора;
- `DOPAFIT_ACCESS_TOKEN_TTL_MINUTES=1` — чтобы истечение сессии проверялось за минуту, а не за 15.
- `DOPAFIT_VERIFICATION_CODE_TTL_MINUTES=1` — чтобы AUTH-04 проверял просроченный код без
  десятиминутного ожидания;
- `DOPAFIT_E2E_ROTATING_VERIFICATION_CODE=true` — только в этом dev-контуре повторная отправка
  для того же адреса и назначения меняет код с `000000` на `000001`, затем на `000002`.
  Так AUTH-05 проверяет отказ старому коду; production-конфигурация этот режим запрещает.

После обычного сида `e2e:reset` добавляет 100 общих упражнений «Каталог E2E» только
в защищённую базу с суффиксом `_e2e`. EX-09/10 проверяют несколько страниц реального
API без изменения пользовательской квоты собственных упражнений. UUID создаёт БД.
Dev/prod-сид эти записи не создаёт.

Контуры разделены по одной причине: прогон имеет право очистить свою базу и не имеет права
очистить вашу. `make e2e-up` пересоздаёт `dopafit_e2e` с нуля — это и есть «известное начальное
состояние», без которого счётчики, уведомления и связи от прошлых прогонов ломают проверки.

PWA и service worker проверяются **только** против прод-бандла (`make e2e-pwa`): в dev-режиме
service worker выключен, а `http://` по LAN-адресу браузер его и не зарегистрирует — нужен
secure context. Цель собирает frontend, запускает отдельный preview и проект `pwa` в общей
сетевой области с ним. Браузер обращается к `http://localhost:4173`: Chromium считает
`localhost` безопасным контекстом. API остаётся на том же origin благодаря preview-прокси.
Подробности — `DEVELOPMENT.md` §11.2–11.3.

## 3. Команды

Обновления релизов проверяют frontend-тесты `app-update` и `app/updates`:
проверка manifest без кэша, подтверждение после взаимодействия, защита тренировки,
outbox и ошибок хранилища, отказ сети, повтор, согласованность SW и сохранение
кэша старых вкладок. `runtime` проверяет заголовки статического `version.json`.
Production-проверки PWA-01/PWA-08 проверяют build ID реального SW, исключение
manifest из precache и обновление обычной веб-вкладки без SW. Полный e2e остаётся
отдельным ручным запуском CI.

Email-шаблоны проверяются backend-тестами `verification-email` и
`auth-integrations`: назначение, код и TTL в HTML/тексте, экранирование,
отсутствие внешних ресурсов и безопасный отказ отправки.
SMTP-тест также собирает MIME без сети: проверяет HTML/текст и вложенные
PNG-логотипы с CID при запрещённом доступе транспорта к файлам и URL.
Проверка не отправляет SMTP-письма и не обращается к стендам.

```
make e2e-up         # поднять контур: пересоздать базу dopafit_e2e, запустить backend-e2e и frontend-e2e
make e2e            # весь набор
make e2e-smoke      # критический путь (@smoke); в CI — по запросу
make e2e-pwa        # раздел J (@pwa) против production preview с service worker
make e2e-issues     # сводка известных дефектов: что воспроизводится, что по безопасности
make e2e-report     # HTML-отчёт последнего прогона
make e2e-lint       # prettier + eslint + tsc для пакета e2e
make e2e-down       # остановить контур
```

Появятся по мере наполнения набора: `make e2e-core` (`@smoke` + `@core`), `make e2e-regression`
(только тесты известных дефектов). Обычные `make e2e` и `make e2e-smoke` работают с dev-контуром;
PWA-тесты запускаются отдельно через `make e2e-pwa`.

Точечный запуск — через `args=`, как у `be-test`/`fe-test`:

```
make e2e args='programs.spec.ts'     # один файл
make e2e args='--grep PROG-06'       # один тест по ID
make e2e args='--grep @security'     # все проверки доступа
```

## 4. Аккаунты, коды, фикстуры

**Демо-аккаунты** (`client@dopafit.dev`, `trainer@dopafit.dev`, пароль `Dopafit1Demo`) создаёт сид.
У них `login_method: "password"`, поэтому **вход по коду для них не работает**: `request-code`
вернёт общий ответ без отправки письма, а `verify-code` ответит «не найдено». Это не дефект —
это свойство фикстуры. Для сценариев входа по коду регистрируйте свежий аккаунт.

**Первый код подтверждения в dev — `000000`** (дефолт `DOPAFIT_DEV_VERIFICATION_CODE` в `backend/src/config.ts`).
В изолированном e2e-контуре первый повтор для того же адреса и назначения даёт `000001`,
второй — `000002`.
Если фиксированный код отключён, настоящий код печатается в лог:
`docker compose logs backend-e2e | grep verification-code`.

**Фикстуры** живут в `e2e/fixtures/` и подключаются через `test.extend`:

| Фикстура | Что даёт | Способ |
|---|---|---|
| `runId` | уникальный префикс прогона для всех создаваемых имён и адресов | — |
| `api` | запросы с Bearer-токеном для подготовки данных | API |
| `freshClient`, `freshTrainer` | новый аккаунт с заполненным профилем | API, три запроса визарда |
| `clientSession`, `trainerSession` | страница с готовой сессией | токены в IndexedDB |
| `linkedPair` | связанная пара клиент-тренер | API |
| `programFixture`, `measurementFixture`, `finishedWorkout` | данные-предпосылка | API |

Принцип: **через UI делается то, что сам тест и проверяет; остальное — через API.** Визард
регистрации проверяют AUTH-01/02 — и только они ведут его кликами. Фикстура `freshClient`
повторяет те же три запроса (`register` → `register/verify` → `users/me/onboarding`), а не кликает
визард: иначе правка одного экрана регистрации красила бы десятки тестов, которым нужен лишь
готовый аккаунт. Связь, программы и замеры готовятся запросами по той же причине.

Свежий аккаунт отличается от демо-аккаунта способом входа: у него `login_method: "code"`, поэтому
OTP-сценарии пишутся только на него. Онбординг фикстура проходит до конца — он пишет профиль и
замер веса на сегодня, без него аккаунт не похож на настоящий.

Данные помечаются `runId` (`client1-<runId>@e2e.dopafit.test`; номер — счётчик аккаунтов внутри
прогона) и убираются за собой. Домен `.test` зарезервирован RFC 2606 — письмо не уйдёт даже при
случайной подмене провайдера.

## 5. Селекторы

Только доступное имя: `getByRole`, `getByLabel`, `getByPlaceholder`, `getByText`. Имена русские —
это язык интерфейса (`getByRole('button', { name: 'Получить код' })`, `getByLabel('Пароль')`).
Эталон стиля — существующие frontend-тесты, например `frontend/src/features/auth/login/LoginForm.test.tsx`.

Маршруты импортируются из `e2e/support/paths.ts`, который реэкспортирует
`frontend/src/shared/config/paths.ts`. Литералы путей допустимы только там — это правило записано
в самом `paths.ts` и распространяется на тесты.

`data-testid` — последнее средство, только там, где семантики действительно нет. Если контрол
недоступен с клавиатуры или не имеет доступного имени, это дефект доступности (UI-01/UI-02),
а не повод привязаться к DOM.

## 6. Viewport и теги

Проверка идёт на **одном** размере экрана. По умолчанию это desktop 1440×900; мобильный размер
запрашивается тегом в имени теста:

| Тег | Проект | Размер | Когда |
|---|---|---|---|
| — | `desktop` | 1440×900 | по умолчанию |
| `@mobile` | `mobile` | 390×844, touch | поведение зависит от касания или от узкого экрана |
| `@narrow` | `narrow` | 320×700, touch | самый узкий телефон: PROG-16, UI-03 |
| `@large` | `large` | 430×932, touch | крупный телефон, другая высота клавиатуры |
| `@pwa` | `pwa` | 1440×900, Chromium secure context | prod preview, manifest, SW и Push |

Теги viewport'а и теги приоритета (`@smoke`, `@core`, `@security`) независимы и совмещаются:
`test('PROG-16 ... @core @narrow')`.

Прогонять каждый тест на всех размерах нельзя: набор последовательный (`workers: 1`), и четыре
проекта умножили бы время на четыре, а одно падение показали бы четырьмя строками. Если проверка
не про вёрстку — она не нуждается в мобильном проекте.

Основные мобильные проекты — Chromium с `isMobile` и `hasTouch`, а не профили устройств Playwright: у профилей
iPhone `defaultBrowserType: 'webkit'`, а ТЗ фиксирует Chromium как матрицу. Drag-and-drop под touch
и под мышью — разные события, поэтому PROG-07 обязан идти в `@mobile`, а не в узком окне desktop.

Исключение: `webkit-viewport` запускает UI-08, UI-10, UI-11 и UI-12 на 390×844 в desktop WebKit.
Он проверяет каркас, навигацию, изменение высоты и моделируемое перекрытие клавиатурой в обеих темах;
это регрессия вёрстки, а не эмуляция системного UI установленного iOS PWA.

## 7. Что запрещено

- **Прод-стенд.** Тесты никогда не обращаются к `app.dopafit.ru` или любому развёрнутому стенду.
- **`pnpm`, `node`, `npx`, `playwright` на хосте.** Только через `make` (`DEVELOPMENT.md` §1).
- **Хардкод идентификаторов.** Никаких UUID программ, упражнений и пользователей в коде теста:
  всё, что нужно, создаёт фикстура.
- **`waitForTimeout` и любые фиксированные паузы.** Ожидается наблюдаемое событие: `expect` с
  авторетраем, `waitForURL`, `waitForResponse`.
- **CSS-селекторы и классы.** Класс — деталь реализации Tailwind, он меняется без изменения поведения.
- **`test.skip` для известного дефекта.** Как оформлять — §9.
- **Markdown-файлы с описанием дефектов.** Находки живут в `e2e/support/known-issues.ts`, см. §9.
- **Секреты и персональные данные в тестах и артефактах.** Пароли, токены, коды и тела сообщений
  не попадают ни в код, ни в отчёт.

## 8. Оракул результата

Тест обязан проверять не только «что-то появилось»:

1. видимый итог в интерфейсе;
2. состояние после `reload` или повторного открытия экрана;
3. для сценариев с двумя ролями — что видит вторая сторона;
4. ожидаемый HTTP-статус, когда он часть проверки.

Сверяются точные значения и количество записей, а не наличие слова «Успешно». Ожидаемый 422 не
должен маскировать неожиданный 500: проверяйте конкретный статус, а не «любую ошибку».

## 9. Известные дефекты

Единственный источник правды — `e2e/support/known-issues.ts`. Никаких отдельных документов:
запись и тест лежат рядом, поэтому не могут разойтись.

```ts
'QA-014': {
  title: 'после разрыва связи тренер сохраняет доступ к замерам и аналитике клиента',
  kind: 'security',
  priority: 'P1',
  cause: 'MeasurementApplication.list берёт карточку через requireCard без требования active',
  tests: ['LINK-08', 'LINK-09', 'SEC-05'],
}
```

Тест пишется на **правильное** поведение и помечается хелпером:

```ts
test('LINK-08 после разрыва связи тренер теряет доступ к замерам @core @security', async ({ ... }) => {
  knownIssue(test, 'QA-014');
  // ...
});
```

`knownIssue` вызывает `test.fail()`: тест запускается каждый прогон и обязан упасть. Поэтому он
всегда скомпилирован и актуален — в отличие от `skip`, который гниёт и к моменту исправления
оказывается нерабочим. Когда дефект починят, Playwright сообщит «unexpectedly passed» — это и есть
сигнал удалить запись.

Поле `kind: 'security'` выделяет находки по доступу и приватности: даёт фильтр
`make e2e args='--grep @security'` и отдельный раздел в `make e2e-issues`.

**Жизненный цикл находки:**

1. Нашли — добавили запись в `known-issues.ts` и тест с `knownIssue()`. Коммит `test:`.
2. Исправили — удалили запись и вызов `knownIssue()`. Тест становится обычным зелёным. Коммит `fix:`.

Если дефект ещё жив, удаление записи сразу делает тест красным — забыть обновить статус нельзя.

## 10. Отчёты и статус

| Что | Где | Сколько живёт |
|---|---|---|
| Отчёт локального прогона | `e2e/playwright-report/` (в `.gitignore`) | до следующего прогона |
| Отчёт и trace упавшего прогона в CI | артефакт job'а | 7 дней |
| Состояние известных дефектов | `make e2e-issues` | всегда актуально |

**Журналы прогонов руками не ведутся.** Историю хранит CI, доказательства падения — trace и
скриншот Playwright. Если нужно «где мы сейчас» — это `make e2e-issues` и зелёный/красный CI,
а не таблица в репозитории.

## 11. Поддержка набора

- **Новая функция** — тест в том же PR, что и код. Уровень выбирается по §1.
- **Flaky-тест** лечится ожиданием наблюдаемого события, а не ретраем и не паузой. Ретрай в CI
  (`retries: 1`) существует для сетевых срывов, а не для гонок в тесте.
- **Тест упал после правки интерфейса** — сначала проверьте, не сломалось ли поведение продукта.
  Подгонять локатор под новый UI можно только убедившись, что сценарий по-прежнему выполняется.
- **Изменился UI авторизации** — после изменения входа, регистрации, восстановления или общих
  OTP-компонентов запускайте весь `make e2e args='auth.spec.ts'` и `make e2e-smoke`.
  E2E проверяет состояние и поведение по доступным ролям, а не дословную формулировку,
  если текст не является предметом проверки. AUTH-12 сравнивает сообщения между типами
  аккаунтов, нормализуя только введённый email и пробелы; конкретная фраза ему не нужна.
- **Изменился контракт** — типы берутся из `contracts/openapi.json` через `make contracts`;
  тесты не описывают формы ответов руками.

## 12. Definition of Done тестовой задачи

- [ ] Тест привязан к ID проверки из [e2e-spec.md](e2e-spec.md).
- [ ] Запускается из чистого состояния и не зависит от порядка соседних тестов.
- [ ] Убирает за собой созданные данные.
- [ ] Прошёл дважды подряд без flaky.
- [ ] `make e2e-smoke` и `make e2e-lint` зелёные.
- [ ] Для дефекта: запись в `known-issues.ts` + тест, который падает до исправления.
- [ ] При изменении продукта — полный DoD из `DEVELOPMENT.md` §5.

## 13. Отладка упавшего теста

```
make e2e-report                      # HTML-отчёт: шаги, скриншот, trace
make e2e args='--grep AUTH-07'       # повторить один тест
docker compose logs backend-e2e      # ответы API и напечатанные коды подтверждения
```

Частые причины:

- **Тест не видит данных.** Проверьте, что `make e2e-up` действительно пересоздал базу, а фикстура
  создавала данные в том же контуре.
- **Запрос ушёл в MSW вместо API.** В прогоне не должно быть обращения к `mockServiceWorker.js`;
  если оно есть — `VITE_API_MOCK` не выключен.
- **Запрос ушёл не в тот backend.** `frontend-e2e` проксирует `/api` по `VITE_DEV_API_PROXY`;
  без этой переменной он уйдёт в dev-backend и тест будет читать чужую базу.
- **Код подтверждения не принимается.** Фиксированный dev-код — `000000`; если он отключён,
  возьмите настоящий из лога backend.

При проверке вкладок учитывайте восстановление последней подстраницы. Ссылки меню
ищутся по доступному имени, а не по `href` корня: адрес ссылки соответствует
сохранённому экрану. Для проверки корневого экрана повторно нажмите активную вкладку.
Тесты потери связи отключают транспорт целиком; доступный API при HTTP 503 или
единичном сбое heartbeat не является отсутствием сети.

После перехода к сохранённым экранам дождитесь признака нужного экрана перед
действием с повторяющимся именем. Например, после «Начать тренировку» проверьте
заголовок «Выбор дня» до выбора дня: одно изменение URL ещё не гарантирует,
что предыдущий экран уже скрыт. Фиксированные задержки для этого не используются.
